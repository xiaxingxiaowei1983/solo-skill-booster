# 评分规则 — SOLO技能创作赛五维度评分模型

> 对齐来源：SOLO技能创作赛官方公告（评审维度：实用性、创新性、完成度、体验感）
> 
> **独创第5维度**：自进化力 — 评价Skill能否从使用中变强，这是本技能的差异化核心
>
> ⚠️ **权重声明**：官方未公开各维度权重，本文件中的权重（实用性25%/创新性20%/完成度20%/体验感15%/自进化力20%）为基于官方评审维度重要性的**推断值**，非官方数据。总分采用5维度简单求和（5-25分制），权重仅用于理解维度相对重要性。

## 总分计算

```
总分 = 实用性 + 创新性 + 完成度 + 体验感 + 自进化力
满分 = 5×5 = 25分
```

## 维度一：实用性（权重30%）

### 1-5分判断标准

| 分数 | 标准 | 关键信号 |
|------|------|----------|
| 5 | 解决真实痛点，有明确用户画像和使用场景，替代现有手工流程 | 写清了"谁在什么场景下省掉了什么"，有before/after对比 |
| 4 | 有使用场景，逻辑自洽，能省掉重复操作 | 场景描述具体，不是泛泛而谈 |
| 3 | 场景模糊但功能存在，需要用户自己找场景 | 只说"可以用来做XX"但没说谁会用 |
| 2 | 功能存在但场景牵强，用不用都行 | 场景是"所有人都能用"=没有场景 |
| 1 | 功能无意义或与已有Skill高度重复 | 手动做更快，或已有同类Skill且无改进 |

### 典型高分表现

- SKILL.md开头1-2句话说清"帮谁做什么省什么"
- 使用场景部分有真实痛点描述（不是编造的）
- 有"做出来之后省掉了哪些动作"的说明
- 目标用户画像具体（如"需要频繁产出社媒内容的运营"）

### 典型扣分表现

- 只有功能描述没有场景（"这是一个XX工具"）
- 场景泛化到"所有人"（=没有场景）
- 没有说清和手动做的区别
- 解决的是伪需求（手动做更快更简单）

### 检查清单（底层判定来源）

| # | 检查项 | 通过标准 | 未通过扣分 |
|---|--------|----------|-----------|
| U1 | 有明确用户画像 | 写清"谁用"（非"所有人"） | -1 |
| U2 | 有真实痛点描述 | 描述了具体痛点（非泛泛而谈） | -1 |
| U3 | 有使用场景说明 | 写清"什么时候用" | -1 |
| U4 | 有before/after对比 | 说明使用前后省掉什么 | -1 |
| U5 | 与手动做有区别 | 说清和手动做的差异 | -0.5 |

### 对应提分方向

| 扣分点 | 提分动作 | 预计提升 |
|--------|----------|----------|
| 无使用场景 | 补充1-2个真实场景，写清谁用、什么时候用、省掉什么 | +1~2分 |
| 场景泛化 | 缩窄到具体用户画像，写出痛点 | +1分 |
| 无before/after | 补充使用前后的对比说明 | +1分 |
| 伪需求 | 重新定位场景，找到真正痛点 | +2分 |

## 维度二：创新性（权重25%）

### 1-5分判断标准

| 分数 | 标准 | 关键信号 |
|------|------|----------|
| 5 | 业界首创或突破性改进，无同类Skill | 在SOLO技能市场找不到同类，或同类但方法完全不同 |
| 4 | 有明显差异化特色，与同类Skill有本质区别 | 能一句话说清"和XX的区别是YY" |
| 3 | 有小创新点，在已有思路上做了改进 | 组合了不同能力，或优化了某个环节 |
| 2 | 功能类似但实现方式不同 | 换了技术栈但效果一样 |
| 1 | 与现有Skill高度雷同，无差异化 | 连触发词都差不多 |

### 典型高分表现

- 组合了没人组合过的能力（如：法律+AI+工作流）
- 用新方法解决老问题（如：用Agent替代传统脚本）
- 有明确的差异化声明（"和XX Skill的区别是YY"）
- 创作过程中展示了创新思考（不是直接搬运）

### 典型扣分表现

- 只说"用AI做XX"但没有说清和手动做XX的区别
- 没有提及同类Skill或没有差异化说明
- 功能和已有Skill高度重叠
- 创作过程只是"让AI帮我写了个脚本"

### 检查清单（底层判定来源）

| # | 检查项 | 通过标准 | 未通过扣分 |
|---|--------|----------|-----------|
| I1 | 有差异化声明 | 写清"和XX的区别是YY" | -1 |
| I2 | 非简单搬运 | 创作过程展示创新思考 | -1 |
| I3 | 有独特组合或方法 | 组合了没人组合过的能力 | -0.5 |
| I4 | 提及同类Skill并对比 | 知道同类存在且说清差异 | -0.5 |

### 对应提分方向

| 扣分点 | 提分动作 | 预计提升 |
|--------|----------|----------|
| 无差异化说明 | 在SKILL.md中增加"与同类Skill的区别"段落 | +1分 |
| 和已有Skill重叠 | 找到差异点并强化，或调整定位 | +1~2分 |
| 创新点不突出 | 在创作过程中展示创新思考，说明为什么这样做 | +1分 |
| 纯搬运 | 重新设计工作流，加入独特环节 | +2分 |

## 维度三：完成度（权重25%）

### 1-5分判断标准

| 分数 | 标准 | 关键信号 |
|------|------|----------|
| 5 | 完整可用，有错误处理、边界情况、降级方案 | 脚本有try-catch，有退出码，有fallback |
| 4 | 核心功能完整，主要路径可用 | 主流程跑通，但边界情况未处理 |
| 3 | 主要功能可用，但缺少错误处理或边界情况 | 能跑但容易崩 |
| 2 | 有明显缺失，部分功能不可用 | 核心功能有bug或缺失 |
| 1 | 只有框架，核心功能不完整 | SKILL.md写了但功能没实现 |

### 典型高分表现

- 脚本有完整的错误处理（try-catch + 错误提示）
- 考虑了边界情况（空输入、网络断开、文件不存在）
- 有降级方案（主方案失败时有备选）
- 脚本有退出码（0成功/1失败/2参数错误）
- 有使用示例和输出样例

### 典型扣分表现

- 脚本里写了input()导致Agent卡死
- 没有错误处理，一出错就崩溃
- 核心功能只有描述没有实现
- frontmatter格式不对导致Agent无法触发
- 依赖未说明，用户不知道要装什么

### 检查清单（底层判定来源）

| # | 检查项 | 通过标准 | 未通过扣分 |
|---|--------|----------|-----------|
| C1 | frontmatter完整 | name+description+version存在 | -1 |
| C2 | 核心功能已实现 | scripts/中有对应实现 | -2 |
| C3 | 有错误处理 | try-catch或等价 | -1 |
| C4 | 无脚本阻塞 | 无input()/readline() | -2 |
| C5 | 有退出码 | 0成功/非0失败 | -0.5 |
| C6 | 依赖已说明 | requirements.txt或依赖说明 | -0.5 |

### 对应提分方向

| 扣分点 | 提分动作 | 预计提升 |
|--------|----------|----------|
| input()阻塞 | 改为命令行参数或配置文件 | +1分 |
| 无错误处理 | 添加try-catch和友好错误提示 | +1分 |
| 功能未实现 | 实现核心功能或标注为"规划中" | +2分 |
| frontmatter错误 | 修正YAML格式，确保name+description存在 | +1分 |
| 依赖未说明 | 添加requirements.txt或依赖说明 | +1分 |

## 维度四：体验感（权重20%）

### 1-5分判断标准

| 分数 | 标准 | 关键信号 |
|------|------|----------|
| 5 | 新手友好，触发词精准，文档清晰，有示例 | 一句话说清怎么用，3步内可上手 |
| 4 | 有文档和示例，基本可用 | 需要读文档但能理解 |
| 3 | 基本可用，但需要摸索 | 能用但不知道怎么触发 |
| 2 | 缺少文档或示例，使用门槛高 | 要读完整SKILL.md才知道怎么用 |
| 1 | 难以使用，触发词不明确 | 不知道什么时候该用这个Skill |

### 典型高分表现

- 触发词精准且不与其他Skill冲突
- 有快速上手指南（QUICKSTART）
- 有使用示例（至少2个）
- SKILL.md结构清晰，渐进式披露
- 输出格式明确，用户知道会得到什么

### 典型扣分表现

- 触发词和其他Skill冲突（如都用"帮我写"）
- 没有使用示例
- SKILL.md太长太乱，找不到关键信息
- 输出格式不明确
- 需要复杂配置才能使用

### 检查清单（底层判定来源）

| # | 检查项 | 通过标准 | 未通过扣分 |
|---|--------|----------|-----------|
| E1 | 触发词精准且无冲突 | 不与其他Skill触发词重叠 | -1 |
| E2 | 有使用示例 | 至少2个示例 | -1 |
| E3 | 有快速上手指引 | QUICKSTART或3步上手说明 | -0.5 |
| E4 | 输出格式明确 | 用户知道会得到什么 | -0.5 |
| E5 | 文档结构清晰 | SKILL.md不超过必要长度 | -0.5 |

### 对应提分方向

| 扣分点 | 提分动作 | 预计提升 |
|--------|----------|----------|
| 触发词冲突 | 添加独特触发词，避免通用词 | +1分 |
| 无使用示例 | 添加2-3个使用示例 | +1分 |
| 文档混乱 | 重构SKILL.md，按标准结构组织 | +1分 |
| 输出不明确 | 添加输出格式说明和样例 | +1分 |
| 配置复杂 | 提供默认配置，减少必填项 | +1分 |

## 维度五：自进化力（提分官独创维度，权重20%）

> 官方四维度评的是"当前状态"，自进化力评的是"未来能不能变强"。
> 这是本技能的独创维度，也是与所有同类评审工具的核心差异。

### 0-5分判断标准

| 分数 | 标准 | 关键信号 |
|------|------|----------|
| 5 | 完整自进化闭环：反馈→沉淀→晋升→验证 | 有retro-log + learned-rules + 自动校验脚本 + 版本迭代记录 |
| 4 | 有结构化复盘+经验沉淀机制，能从使用中吸收改进 | 有复盘日志、经验可写入、版本有changelog |
| 3 | 有反馈入口或经验记录机制，但未形成闭环 | 有evals或用户反馈收集，但经验无法自动沉淀 |
| 2 | 有版本号声明或changelog，但无实际进化路径 | frontmatter有version但无复盘/无经验沉淀 |
| 1 | 纯静态SKILL.md，无任何进化机制 | 无retro/无版本/无反馈入口 |
| 0 | 零进化能力，无法从使用中学习，Skill注定过时 | 纯输出型，规则/词库无法更新，无任何改进机制 |

### 典型高分表现

- 有retro-log复盘吸收机制，每次使用后经验可沉淀
- 有learned-rules经验晋升规则，重复模式自动升级为规则
- 有自动化校验脚本（validate_skill.py等），质量可自动检查
- 版本迭代有记录（changelog），改进可追溯
- 用户反馈有收集入口，能驱动Skill改进

### 典型扣分表现

- 纯静态输出，用完即弃，无法从使用中学习
- 词库/规则硬编码，无法更新，Skill注定过时
- 踩坑经验真实但无结构化沉淀机制
- 无版本号或版本号只是摆设，无实际迭代
- 依赖外部数据源但无自动更新机制

### 检查清单（底层判定来源）

| # | 检查项 | 通过标准 | 未通过扣分 |
|---|--------|----------|-----------|
| S1 | 有retro-log或复盘机制 | references/有retro-log | -1 |
| S2 | 有版本号+changelog | frontmatter.version + CHANGELOG | -1 |
| S3 | 有用户反馈入口 | SKILL.md有反馈说明 | -1 |
| S4 | 有经验晋升规则 | 有learned-rules或等价 | -1 |
| S5 | 有自动化校验脚本 | scripts/有validate脚本 | -1 |

### 对应提分方向

| 扣分点 | 提分动作 | 预计提升 |
|--------|----------|----------|
| 纯静态无进化 | 添加retro-log模板+版本号声明 | +2分 |
| 词库/规则无法更新 | 添加自动更新脚本+数据源刷新机制 | +2分 |
| 无反馈入口 | 添加用户反馈收集+经验沉淀机制 | +2分 |
| 无自动化校验 | 添加validate脚本+质量门控 | +2分 |
| 零进化能力 | 从零搭建：版本号+changelog+复盘日志+校验脚本 | +4分 |

### 自进化力评分证据清单

| 证据项 | 存在即加分 | 检查方式 |
|--------|-----------|----------|
| retro-log或复盘吸收机制 | +1 | 检查references/是否有retro-log |
| 版本号+changelog | +1 | 检查frontmatter.version + CHANGELOG文件 |
| 用户反馈收集入口 | +1 | 检查SKILL.md是否有反馈说明 |
| 经验晋升规则（learned-rules） | +1 | 检查是否有经验沉淀文件 |
| 自动化校验/测试脚本 | +1 | 检查scripts/是否有validate脚本 |

## 硬性规则（违反即触发）

> 以下规则是评分底线，不需要逐条判断1-5分，违反即直接限制对应维度。硬性规则优先于评分校准规则。

| # | 硬性规则 | 触发条件 | 强制结果 |
|---|----------|----------|----------|
| H1 | 脚本含input()阻塞 | scripts/中任何.py文件含input()或readline() | 完成度 ≤ 2 |
| H2 | 硬编码敏感信息 | 代码中含API Key/密码/Token明文 | 发布门控直接FAIL |
| H3 | frontmatter缺失 | SKILL.md无YAML frontmatter或缺少name/description | 完成度 ≤ 1 |
| H4 | 无使用场景 | SKILL.md未说明谁在什么场景下使用 | 实用性 ≤ 2 |
| H5 | 纯静态无进化 | 无retro-log/无版本号/无反馈入口/无校验脚本 | 自进化力 = 0 |
| H6 | 触发词与已有Skill冲突 | 触发词完全覆盖已有Skill的触发词 | 体验感 ≤ 2 |
| H7 | 核心功能未实现 | SKILL.md描述了功能但scripts/中无对应实现 | 完成度 ≤ 1 |
| H8 | 依赖未说明 | 有scripts/但无requirements.txt或依赖说明 | 完成度 ≤ 3 |

### 硬性规则检查流程

```
评分前先检查硬性规则
       │
       ├── 命中H1 → 完成度直接≤2，跳过完成度1-5分判断
       ├── 命中H2 → 门控直接FAIL，无需继续评分
       ├── 命中H3 → 完成度直接≤1
       ├── 命中H4 → 实用性直接≤2
       ├── 命中H5 → 自进化力直接=0
       ├── 命中H6 → 体验感直接≤2
       ├── 命中H7 → 完成度直接≤1
       ├── 命中H8 → 完成度直接≤3
       └── 未命中任何硬性规则 → 正常1-5分判断
```

## 评分校准规则

1. **先看实用性**：如果实用性≤2，其他维度上限3分（没有场景的功能没有意义）
2. **完成度底线**：如果完成度≤2，体验感上限2分（功能不完整谈不上体验）
3. **创新性独立**：创新性不受其他维度影响（功能简单但思路新颖可以高分）
4. **体验感加分**：体验感≥4时，总分额外+0.5（好体验值得额外奖励）
5. **自进化力底线**：如果自进化力=0，发布门控直接降一级（没有未来的Skill不值得PASS）
